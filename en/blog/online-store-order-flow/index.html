What an online store includes: catalogue, cart, payment and integrations

Elena · 2026-11-18

The catalogue shows products, the cart collects the selected items, and checkout passes the order to the seller. Online payment, automatic delivery and exchange with an accounting system add separate scenarios. Before getting a quote it helps to describe each of them.

The minimal path from product to order

Category: the buyer finds the right group of products. Product card: sees the name, price, image and agreed details. Cart: checks items, quantity and total, can remove extras. Checkout: passes contact details and the order contents. Seller's side: the order appears in the agreed place, and the buyer gets a clear answer about acceptance or an error.

If the customer only sends a request and a manager confirms availability, name the action accordingly: “Send order for confirmation”. Do not promise automatic availability confirmation or payment if they are not implemented.

For a payment service, check its requirements and connection terms in advance: this article covers the scope of development, not a particular business's readiness to accept payments.

What to prepare for the catalogue

Start with a small table of real products: a simple product, a variant with an attribute and an item with limited availability. Agree whether sizes and colours count as separate products or as variants: this affects the catalogue model.

You need: a stable ID or SKU that does not change with the name; name, category, description and attributes; price, currency and selling unit (piece, set, pack); availability and a rule for an empty value; image files clearly matched to products; weight and size if delivery needs them.

Example brief for a small store

An illustrative example, not a completed order. Catalogue: 24 products and three categories. A product has one price, one main image and a short description. The customer builds a cart and sends a request to a manager. At the first stage there is no payment on the site, no customer account and no automatic delivery calculation. The manager checks availability and replies via the given contact. The way of receiving requests and the procedure for changing products must be agreed.

Such a description separates the first version from later tasks. If prices change daily, add the update requirement immediately: replacing files by hand and automatic loading are different processes.

How to accept the work without a real payment

1) In an agreed test environment put two different products in the cart, change the quantity and remove one item. 2) Compare the total, units and request contents with the seller's data. 3) Check required fields, a wrong contact and a repeated button press. 4) Make sure empty availability and zero price are handled by the defined rules. 5) If integrations were ordered, check them separately with test data, including the external service being unavailable; test payment only in the service's own test mode. 6) Get the source code, installation instructions and a description of the update procedure, and agree support after handover separately.

When the next stage is needed

It makes sense to tie each extension to a specific manual task: an employee copies requests over, often edits stock or calculates delivery separately. Write down the frequency and an example of the operation: this makes it easier to choose the right integration than ordering the whole list of features at once.
